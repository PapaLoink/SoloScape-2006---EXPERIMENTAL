## Executive conclusion

The project has a strong revision-443 technical foundation, but it is **not yet an accurate 18 December 2006 recreation**. The cache/map/client base is much closer than the gameplay/content layer.

The largest blockers are: enabled Grand Exchange; active 2008-style bank tabs; Tutorial Island Ironman/UIM/HCIM; the wrong Christmas event; missing Hunter and functional Construction; incomplete quests; missing 2006 activities; and unresolved interaction coverage.

Severity: **P0** = visible date blocker, **P1** = major target content missing, **P2** = authenticity/coverage debt, **VERIFY** = needs behavioural evidence, **OK** = target-aligned, **GATED** = later code present but disabled.

## 24. Continuation audit: build-443 ID semantic collisions

The revision-443 cache overlay is correct enough to decode period item names, but legacy/custom server logic still assigns later or custom meanings to genuine 443 IDs. This is more dangerous than merely retaining dormant post-2006 classes because legitimate target-era items can enter those code paths.

### P0/P1 - boss-pet logic hijacks Construction items on Drop

`PetManager.petItemNpcPairs` maps 8070-8073 to KBD/KQ/Chaos Elemental/Jad pet NPCs. `CombatManager.finishDeath()` unlocks those pets on boss kills. `ItemActionPacketHandler.handleDropItem()` checks the pet table before ordinary drop handling, summons the pet, and returns.

Actual bundled build-443 definitions decode those IDs as:

- 8070 = Steel torches
- 8071 = Steel candlesticks
- 8072 = Gold candlesticks
- 8073 = Incense burners

Therefore a strict-443 player attempting to Drop one of these legitimate Construction items is routed into boss-pet behaviour instead of ordinary item dropping. Construction is currently incomplete, so this is partly masked today, but restoring Construction will make the collision directly reachable.

**Fix:** disable boss pets in strict mode or move their token identity entirely outside the 443 item namespace. Never dispatch pet behaviour from these four target-cache IDs.
### P1/P2 - custom Necromancy reuses Construction flatpack IDs

The custom `Spellbook.NECROMANCY` uses interface 19104. `MagicSpellAction.necromancyReanimationTable` consumes even IDs 8080 through 8116, and `ItemActionPacketHandler` has explicit `case 8118` logic that toggles the Necromancy spellbook. `NecromancyReanimateTask` also treats 8118 as its relevant equipped item.

The same IDs in the actual 443 cache are Construction items: Bells, statues, portraits, decorations, benches, dining tables and related flatpacks; 8118 is **Teak table**. Their native inventory definitions do not advertise a Necromancy action.

This does not prove ordinary UI clicks currently trigger every custom handler, but it is a hard semantic collision and a packet-level/custom-client reachability risk. It will also conflict directly with a faithful Construction implementation.

**Fix:** strict mode should remove/gate `Spellbook.NECROMANCY`, interface 19104, the reanimation table and all item handlers that reinterpret 8080-8118. Note that the real 2006 `Necromancy book` is item 4837 from Zogre Flesh Eaters; that historical item is unrelated to this custom spellbook.

### P2 - legacy â€œskillcape bundleâ€ ranges also overlap genuine 443 items

`ShopManager.isSkillcapeBundleItem()` treats 7992-7997, 8001-8012 and 8016-8065 as special cape bundles. In build 443 these ranges contain real content such as stuffed fish, portraits, teleport tablets, enchant tablets and many Construction flatpacks/furniture items.

Current `Shops.dat` reflection did not find these suspicious ranges in original shop stock, so this appears dormant at present. It is still unsafe legacy logic: if any such item is stocked, purchase handling can reserve extra slots and substitute adjacent item IDs.

**Fix:** delete the numeric-range heuristic. Identify actual cape products explicitly by the real build-443 cape/hood IDs and seller rules.

## 28. P0 - unrestricted player cheat commands invalidate strict progression

This is a normal-client reachable blocker. The bundled client sends any chat beginning with `::` using command opcode 174 (`Client/src/jagex/io/Buffer.java`). `CommandPacketHandler` accepts opcode 174 and forwards it directly to `Player.handleCommand()` with no rights check.

`Player.handleCommand()` dispatches many privileged/game-breaking commands **before** its later `playerRights` logic, and `executeCheatCommand()` itself has no permission guard. Normal command traffic can therefore reach functionality including:

- `::master` / `::setlevel` - set skills directly
- `::money`, `::runes`, `::food`, `::arrows`, `::nbones` - inject resources
- `::bank` - open the bank anywhere
- `::god` - toggle god mode
- `::quests`, `::cquest`, `::rquest` - mutate quest completion
- `::tele` - move to arbitrary coordinates
- `::tp` - open the developer World Teleports selector
- `::run` / `::irun`, `::music`, `::pray`, spellbook switching and other conveniences

`WorldTeleportMenu` explicitly describes itself as a developer convenience and offers free teleports to 24 locations through custom interface 19600.

**Impact:** economy, progression, quest, travel, death/combat and timing tests are not meaningful on an ordinary account while these commands are reachable.

**Fix:** enforce authorization at the command-dispatch boundary. In strict mode, ordinary players should receive only historically appropriate/social commands; developer cheats should require explicit staff/debug authorization and preferably be disabled entirely outside a development profile.

## 29. P0/P1 - death piles use post-target privacy/timing and destroy recoverable untradeables

The target-date PvM death mechanic was harsher than the current server. Jagex's 16 Oct 2007 LootShare update explicitly introduced a new one-minute private recovery window and stated that **previously, monster-death items appeared instantly for everyone**. Contemporary Oct 2007 player discussion also records the old death pile as immediately visible and lasting about one minute.

Current code does the opposite: `Player.dropDeathItems()` creates ordinary lost tradeables as PRIVATE ground items, and `GroundItemManager` waits 100 seconds before making them PUBLIC. The timer is then reset and the default config keeps public ground items for another 200 seconds (`[ITEMS_STAY_ON_GROUND_TIME];200`), yielding a much safer/longer death-pile lifecycle than the Dec 2006 target.

There is a second mismatch in untradeables. `Player.dropDeathItems()` skips every untradeable item unless it is handled as degraded Barrows equipment. Contemporary 2006 evidence shows this rule was item-specific instead: many untradeables such as Fire capes, god books/staves and Construction heraldic equipment could remain on the ground for roughly two minutes for the owner, while some items such as Runecrafting pouches disappeared on death.

The kept-item selection itself is directionally correct: `DeathItemValueComparator` sorts by High Alchemy value, matching the old pre-GE death-protection basis.

**Fix:** implement target-era death ground-item semantics separately from ordinary dropped-item semantics: instant public visibility for tradeable PvM death piles, the correct short death lifetime, immediate killer access in PvP, and an explicit per-item/class rule table for recoverable versus destroyed untradeables. Do not use one global `isUntradeable()` discard rule.

## 30. P0/P1 - the ordinary NPC spawn population is still essentially revision 377 / May 2006

This is one of the largest structural mismatches found. `data/npcs/Npc spawn.dat` contains 4,942 spawn records. Direct decoding of its own format gives an ID range of 0-3864, with only five records above 3851 (three unique IDs). `GameplayHelper.loadNpcSpawns()` then explicitly rejects `value7 > 3851` and also rejects NPC 3852, so the normal static population effectively stops at NPC ID 3851.

The repository's own `CacheRevisionInfo` records revision **377 (2 May 2006)** as having 3,852 NPC definitions, exactly IDs 0-3851. By contrast, the bundled target cache decodes 5,193 NPC definitions for build 443. This means the map/definitions are December 2006, but the ordinary NPC placement dataset is still anchored around the 2 May 2006 definition boundary.

A source-wide scan of explicit `spawnNpc...` calls found no normal late-2006 replacement population: excluding the separately gated God Wars manager, the only explicit spawn above 3851 is NPC 3863, the custom Grand Exchange NPC spawned when GE is enabled.

**Impact:** NPCs introduced or renumbered from May through 18 Dec 2006 cannot be assumed to exist in the world at all. This structurally affects Construction, Hunter, later quests, late-2006 shops/dialogues, the 18 Dec Christmas event, and any other target-era content whose NPCs use the post-377 ID range. It also explains why correct build-443 definitions alone do not make the world historically complete.

**Fix:** replace the revision-377-era NPC spawn dataset with a revision-443/18-Dec-2006 population source, or build an explicit historically sourced 443 spawn overlay. Remove the `>3851` cutoff in strict-443 mode only after the population data itself is correct. Add an audit test that reports spawned definition IDs by release interval and verifies known post-May-2006 NPCs are present at their target coordinates.

## 31. P0/P1 - mixed NPC drop tables actively leak June 2007 rewards into the 2006 world

`data/npcs/Npc drops.dat` is not a pure build-443 dataset: it allocates table slots through NPC ID 6432 and contains many later item IDs. `NpcDropTable.isAllowedDrop()` uses `ItemDefinition.isDefined(itemId)` as the main availability check. Because the project's custom item metadata defines IDs beyond the native 443 cache ceiling (10511), later rewards can pass this check.

A reflection audit of the raw drop arrays found 118 configured entries with item IDs >=10512. Most belong to later NPCs that are not normally spawned, but **two are attached to NPC IDs that are part of the live revision-377-era population and therefore are reachable in strict-2006 play:**

- NPC 50 (King Black Dragon) has weighted drop **11286, Draconic visage**. The visage/Dragonfire Shield update was released 18 June 2007.
- NPC 2783 (Dark beast) has weighted drop **11235, Dark bow**. The Dark bow was released 11 June 2007.

Both item IDs currently return `ItemDefinition.isDefined(...) == true`, so the historical availability filter does not reject them.

Separately, `NpcDropTable.isAllowedDrop()` hard-rejects item IDs 7956-8118, an old revision-boundary heuristic. The current raw drop file contains zero entries in that band, so it is not causing an observed live omission today, but it is still unsafe for a 443 dataset and should be removed in favour of explicit historical availability.

**Fix:** filter NPC drops against an authoritative 18-Dec-2006 item/reward allowlist, not custom-definition existence or numeric ranges. Add a regression that enumerates every reachable static NPC's raw drops and fails if any item was released after the target date. Specifically remove 11286 from KBD and 11235 from dark beasts in the strict-2006 profile.

## 32. P1 - Lunar spellbook is completely missing

The 18-Dec-2006 target must include Lunar magic. Lunar Diplomacy released on 24 Jul 2006 and introduced a new spellbook; Lunar Home Teleport was added on 27 Sep 2006. Later 2007 Lunar additions must remain excluded.

## 41. P1 - default combat branch has incorrect player defence rolls

`ServerSettings.modernCombatSystemEnabled` defaults **true**. The melee max-hit and hit-chance equations in that branch are not inherently post-2006; several are algebraically the familiar RS2 formulas. Do **not** fix this by blindly switching to the legacy branch.

Two default defence-roll paths are concretely wrong:

- **Magic defence:** `calculateDefenceRoll()` uses `(Magic level + 9) * (magic defence bonus + 64)` for a player and ignores Defence level. Contemporary evidence exists: a Tip.It post dated **28 Feb 2006** reproduces a Jagex support response stating that magical defence is split **70% Magic / 30% Defence**. The target therefore predates neither the rule nor the evidence for it. This bug heavily distorts builds with unequal Magic/Defence levels.
- **Ranged defence:** the same method uses raw `(Defence level + 9) * (ranged defence bonus + 64)`. Unlike its melee-defence branch, it does not apply Defence prayer multipliers or the player's Defensive/Controlled stance bonus. Steel Skin already increased effective Defence by 15% in this era, so ranged attacks currently bypass part of the intended Defence benefit.

There are also off-by-one candidates to golden-test: player Magic attack uses `+9` where the standard player formula uses `+8`, while NPC melee/ranged attack uses `+8` where NPC rolls conventionally use `+9`. These should be verified against period vectors rather than guessed.

**Fix:** keep one evidence-backed RS2 formula path and add golden tests for melee/ranged/magic attack and defence rolls across low/high levels, prayers and combat styles. At minimum, restore the 70/30 player Magic-defence split and make Ranged defence use the same effective-Defence calculation as melee before style-specific equipment bonuses are applied.

## 46. Positive finding - run-energy drain/recovery matches the pre-rework model

The original `VERIFY` concern around ordinary run energy can be closed positively. `MovementQueue` drains raw energy once per running tick using a clamped carried-weight term equivalent to the legacy formula `67 + (67 * weight / 64)`, with weight clamped to 0..64 kg. `Player.restoreRunEnergy()` stores energy on the historical 0..10,000 scale and restores `8 + floor(Agility / 6)` raw units each 0.6-second tick while not running. These are later duplicate heraldic-shield IDs and are **outside the bundled 443 item cache, whose highest stock item ID is 10511**. `NpcDropTable.isAllowedDrop()` nevertheless accepts them because `ItemDefinition.isDefined()` also trusts the later custom metadata namespace. Their configured chances are 1/1404 each per easy reward roll and 1/1625 each per hard reward roll, so this is reachable, not dead data.

The target cache already contains the correct shield IDs: easy black heraldic shields `7332/7338/7344/7350/7356`, medium adamant shields `7334/7340/7346/7352/7358`, and hard rune shields `7336/7342/7348/7354/7360`. The medium table already uses the correct namespace, making the easy/hard 106xx entries a clear migration error.

**Fix:** implement the 5-Dec emote-clue/Uri flow from target data; replace the ten 106xx reward entries with their native 443 IDs; and make all clue rewards pass the same strict target-content availability policy proposed in finding 39. Add tests asserting every rollable reward exists in the stock 443 item config group and that representative easy/medium/hard emote clues can be completed end-to-end.
## 52. P2 - Farming is broadly present, but potato growth uses the wrong global cycle
- The Farming subsystem is comparatively complete: persisted patches, offline/login catch-up, watering, disease/death, farmer protection, compost/supercompost, compost bins, allotments, flowers, herbs, hops, bushes, trees, fruit trees and special patches are all represented.
- `FarmingPatchUtils` uses globally aligned crop-family windows and the main families resolve to the expected legacy cadences (5-minute flowers, 10-minute allotments/hops, 20-minute herbs/bushes, 40-minute trees, etc.).
- `AllotmentCropDefinition.POTATO` is an exception: it stores total growth `40` with config stages `10 -> 13`, and `getGrowthCycleTicks()` computes `40 / (13 - 10) = 13` minutes.
- Target-era potatoes grow over four 10-minute Farming cycles (40 minutes total), not three approximately 13-minute windows.
- The total elapsed growth time is therefore only slightly off, but watering expiry/disease opportunities and global tick alignment occur on the wrong cadence for potatoes.
- This is a narrow balance/timing defect, not evidence that Farming as a whole needs replacement.

## 53. P1 - the 31-Jul-2006 crossbow production/enchantment system is only half migrated
- `SmithableItemDefinition` correctly includes the July-2006 metal bolt sets, bronze-through-rune crossbow limbs and mithril grapple tips.
- The corresponding Fletching pipeline is not present. Source-wide searches find no recipes for attaching the six limb types to wooden stocks, no crossbow-string assembly path, and no normal production route for the resulting unfinished/finished metal crossbows.
- `GemBoltTipDefinition` only handles the older opal/pearl route. The 31-Jul-2006 sapphire/emerald/ruby/diamond/dragonstone/onyx bolt-tip family is absent from Fletching.
- The Magic code likewise has no Enchant Crossbow Bolt handlers for the new enchanted bolt family.
- This is target-valid content: metal crossbows, crossbow string, sapphire+ bolt tips and their enchanted forms were part of the 31-Jul-2006 Crossbows update.
- Combat classification for ordinary named metal crossbows is at least usable: they fall onto the generic crossbow profile with the expected slow crossbow cadence, so this finding is primarily production/ammunition completeness rather than total weapon failure.
- Remediation: implement the stock/limb/string recipes, new gem-tip attachments and target-era Enchant Crossbow Bolt spells against the 443 item namespace; do not key their availability off merged custom item metadata.

## 54. P1 - Redemption consumes all Prayer but never heals
- The combat hit pipeline correctly checks for active Redemption after a non-lethal hit leaves the player below 10% Hitpoints.
- `PrayerManager.triggerRedemption()` calculates `floor(basePrayer / 4)`, which is the correct target-era heal amount, and correctly drains Prayer to zero/deactivates prayers.
- However, the calculated healed Hitpoints are never written back to the player/entity. The method contains an ineffective max-HP check (`entity.getMaxHitpoints();`) but no `setCurrentHitpoints(...)` call.
- Result: Redemption triggers visually and destroys the player's remaining Prayer points while providing **zero healing**.
- Smite (`floor(damage / 4)` Prayer drain) and Retribution (random damage up to base Prayer / 4) are structurally consistent with the period and do not share this defect.
- Fix: apply the calculated heal to the player's current Hitpoints, capped at max Hitpoints, before zeroing Prayer; retain the existing non-lethal/below-10% trigger semantics.

## 55. P1 - Giant Mole and its Wyson reward loop are missing despite being March-2006 content
- The Giant Mole was added on 7-Mar-2006, well before the target date and before the server's May-2006 NPC-population cutoff.
- The build-443 content metadata contains NPC `3340` (Giant Mole), item `7416` (Mole claw) and item `7418` (Mole skin), but the loaded binary NPC spawn table contains no NPC 3340 entry.
- Source-wide checks find no Giant Mole spawn/controller, low-health burrow/reposition mechanic, or dedicated Mole combat implementation.
- Mole claw/skin also have no gameplay references, and there is no Wyson exchange path converting the proof items into bird nests.
- Canoes from the same 7-Mar-2006 update are substantially implemented, so this is not simply a whole-update/cache omission; the Mole branch was never migrated.
- Remediation: add the Falador mole-lair entry/spawn, target-era Giant Mole combat and low-health burrowing, period drop table, and Wyson claw/skin exchange. Keep later reworked Mole mechanics out of the 18-Dec-2006 profile.

## 56. P1/P2 - the 5-Dec-2006 Magic composite bow is missing its Powershot special attack
- Item `10284` (Magic comp bow) is target-valid content released with the 5-Dec-2006 Treasure Trails update and is already present in the active hard-clue reward table.
- The combat classifier recognizes it correctly as `WeaponProfile.SPECIAL_BOW`, so its ordinary attack cadence/ammunition path is live.
- `SpecialAttackDefinition`, however, creates `MagicLongbowSpecialDefinition(35, new String[0])`; the derived default match pattern is only `"magic longbow"`.
- A runtime probe confirms `SpecialAttackDefinition.forItem(new ItemStack(10284)) == null` while the weapon profile is `SPECIAL_BOW`.
- Historically the Magic composite bow shared the Magic longbow's Powershot special at **35%** energy. Contemporary discussion on 9-Dec-2006 explicitly describes it as the same special as the MLB.
- Result: a legitimate newly released target-date clue reward can be wielded and fired normally, but has no special attack despite one being part of the item on the target date.
- Fix: include `"magic comp bow"` in the Magic-longbow/Powershot special definition (or map by item/profile rather than fragile display-name matching) and retain the 35% energy cost.

## 57. P1/P2 - Dragon battleaxe Rampage uses a flat +20% Strength boost instead of the 2006 drain-based formula
- `performDragonBattleaxeSpecial()` currently boosts Strength by `floor(baseStrength * 0.20)`, then drains 10% of base Attack, Defence, Ranged and Magic.
- A contemporaneous Tip.It correction from 26-Jul-2006 reports a player at 70 Strength being boosted to 87 by Rampage; a flat 20% boost would only reach 84.
- The legacy formula is `10 + floor(totalLevelsDrained / 4)` Strength, where each of Attack/Defence/Ranged/Magic loses `floor(currentLevel * 0.10)`.
- Example at 70 in all four drained stats: 7+7+7+7 = 28 levels drained; Strength boost = 10 + floor(28/4) = 17, reproducing the observed 70 -> 87 result exactly.
- The current implementation also calculates drains from base levels rather than current levels, so prior potion boosts/stat drains interact incorrectly with Rampage.
- The 100% special-energy cost, animation/graphic and forced text are otherwise structurally correct.
- Fix: compute the actual drain amounts from current Attack/Defence/Ranged/Magic, apply those drains, then boost Strength by `10 + floor(totalDrained / 4)` with the target-era cap/restore behaviour.

## 58. P1 - Abyssal whip special attack is still the pre-Jun-2005 max-hit-or-miss version
- `AbyssalWhipSpecialAttack.prepareSpecialAttack()` randomly sets max hit to zero 50% of the time; otherwise it keeps the full calculated max hit.
- It then creates an `alwaysHits` hit without `enableRandomDamage()` or an accuracy check. In `CombatAction`, that means the special deals either exactly **0** or exactly the weapon's **maximum hit**, and cannot miss through normal defence rolls.
- That reproduces the whip's original launch-era special behaviour, which was changed on **22-Jun-2005**, more than a year before the 18-Dec-2006 target.
- By the target date, Energy Drain consumed 50% special energy, performed a normal-damage attack with **+25% accuracy**, and in PvP transferred **10% of the target's run energy** to the wielder (with the target receiving the drain message).
- Source-wide search finds no whip-specific run-energy transfer or `"You feel drained!"` handling, so the post-Jun-2005 effect is not implemented elsewhere.
- Fix: remove the 50/50 zero-or-max logic and `alwaysHits`; roll normal damage with a 1.25 accuracy multiplier, then on a successful PvP hit transfer 10 percentage points of run energy from target to attacker, capped appropriately, and send the period message.

## 59. P1/P2 - Magic longbow and Seercull one-shot specials consume two arrows; Powershot is not guaranteed to hit
- `MagicLongbowSpecialAttack` creates exactly one projectile/one hit, but replaces the ordinary one-arrow ammunition requirement with `MagicLongbowArrowRequirement`, whose constructor hardcodes an amount of **2**. Powershot therefore consumes two arrows for one shot.
- The same copy-pattern exists in `SeercullSpecialAttack`: it creates one projectile/one hit but `SeercullArrowRequirement` also hardcodes **2** arrows.
- Magic longbow Powershot is implemented with a `5.0` accuracy multiplier plus an ordinary accuracy check. That makes it highly accurate but still capable of missing; target-era Powershot was a guaranteed-hit attack and cost 35% special energy.
- Seercull Soulshot likewise uses an ordinary accuracy check; the established legacy/Old School behaviour is a guaranteed hit that drains Magic by the damage dealt. Its 100% energy cost and damage-based Magic drain are otherwise represented.
- These are normal, reachable 2006 weapons, so the extra ammunition consumption and miss chance affect ordinary target-era combat rather than dormant later content.
- Fix: charge one arrow for Powershot/Soulshot, use the target-era always-hit semantics, and keep one projectile/one damage roll. When section 56's Magic composite bow Powershot is restored, route it through the same corrected one-arrow guaranteed-hit implementation.

## 60. P1 - Dragon spear Shove has its push-size check inverted and stuns for too long
- `DragonSpearSpecialAttack` correctly creates a zero-damage, always-hit Shove and costs 25% special energy.
- Its effect handler calculates the tile away from the attacker, but then sets `canMoveTarget = target.getSize() > 1` and only performs the knockback when that is true.
- Normal players use the one-tile/default entity size and therefore are **not pushed at all**. Conversely, larger NPCs are eligible for movement even though the period Shove was intended for one-square targets and did not work on large monsters.
- The handler then sets `stunTimer` to **10 game ticks**, i.e. about **6 seconds** at the server's 0.6-second tick. Period descriptions put Shove's stun at roughly 3 seconds (later documentation commonly gives 3.6 seconds), so the implemented lock is materially too long.
- Result: one of the Dragon spear's defining 2006 PvP/Castle-Wars uses is broken: players are stunned in place rather than shoved one tile, and remain disabled too long.
- Fix: allow knockback only for valid one-tile targets when the destination tile is legal, reverse/remove the current `> 1` size condition, and use the target-era stun duration (about 5-6 ticks rather than 10).

## 61. P2 - Dragon 2h Powerstab can hit 15 targets instead of the historical 14-target cap
- The primary Powerstab hit is queued normally, then `specialEffectId 6` scans nearby players/NPCs in multicombat and queues additional hits.
- `queuedTargets` counts only those extra targets and breaks when `++queuedTargets > 13`, allowing **14 additional** hits after the primary target.
- Total possible targets from one special are therefore **15**, while the documented legacy Powerstab cap is 14 enemies total.
- The 60% energy cost, 3x3/adjacent multicombat concept and ordinary per-target damage rolls are otherwise represented.
- Fix: count the primary target toward the cap or stop after 13 additional targets.

## 62. P1/P2 - Magic shortbow Snapshot increases accuracy instead of reducing it
- `MagicShortbowSpecialAttack` correctly creates two rapid projectiles/hits, consumes two arrows, and uses the target-era 55% special-energy cost.
- Both hit definitions, however, use `setAccuracyMultiplier(1.1)`, giving each arrow a **10% accuracy increase** over a normal shot.
- The target-era special was explicitly the opposite: Snapshot fired two arrows rapidly with **reduced accuracy**. A January-2006 Tip.It discussion even contrasts the RuneScape manual's increased-accuracy dragon dagger special with the magic shortbow's stated reduced accuracy.
- This is a reachable PvP/PvM balance error: the server combines Snapshot's burst benefit with an accuracy bonus it should not have.
- Fix: replace the 1.10 multiplier with the historically sourced reduced-accuracy modifier; retain two arrows/two projectiles and the 55% cost.

## 63. P1/P2 - Rune thrownaxe Chain Hit charges 10% once instead of 10% per target
- `RuneThrownaxeSpecialDefinition` has a 10% energy cost, and the generic `WeaponCombatAttack` path deducts that cost exactly once when the special attack begins.
- `RuneThrownaxeSpecialAttack` can then chain from the primary target to as many as five additional valid targets, for six hits total, without any further special-energy deduction.
- The target-era Chain Hit cost was **10% of the special bar per target hit**; historical guides describe a six-target chain as consuming up to 60%.
- The current implementation therefore gives the full maximum chain for only one-sixth of the intended energy cost in the most crowded case.
- The one-thrownaxe projectile/resource concept and six-target upper bound are otherwise consistent with the legacy special.
- Fix: reserve/check sufficient energy as the chain progresses and deduct 10 percentage points for each target actually hit/queued, stopping the chain when fewer than 10 points remain.

## 64. P1 - Darklight Weaken does not work on NPCs/demons and uses the wrong drain amount

`DarklightSpecialAttack` assigns `specialEffectId(4)`. In `SpecialAttackDefinition.applyHitSpecialEffect()`, case 4 immediately exits unless the target is a player, then drains only 5% of the player's base Attack, Strength and Defence.

Target-era Weaken is specifically meant to work on NPCs as well as players, and is twice as effective against demons: 5% of base level + 1 normally, 10% + 1 against demons, on a successful hit.

**Impact:** Darklight's defining 2006 PvM special has no stat-drain effect at all against demons or any other monster; its PvP version is also slightly under-strength.

**Fix:** move the drain onto a target-stat abstraction that supports NPC combat stats, classify target-era demons explicitly, and apply 5%+1 or 10%+1 to Attack/Strength/Defence after a successful hit. Add player, ordinary-NPC and demon regression cases.
## 65. P2 - Dragon halberd Sweep omits its multi-combat area attack

`DragonHalberdSpecialAttack` correctly gives the selected target +10% max damage and adds a second, 25%-less-accurate hit when the target occupies more than one tile. However, the class only creates hit definitions for that selected target, and a source-wide search finds no later Dragon-halberd-specific fan-out handler.

Target-era Sweep also attacked nearby enemies in multi-combat areas; that area component is part of the same 30%-energy special.

**Impact:** the special is correct against a single large monster but incomplete in multi-combat, reducing one of the weapon's defining uses.

**Fix:** when the attacker is in a valid multi-combat context, enumerate the period-correct adjacent sweep area, validate every secondary target with the normal combat rules, and queue the +10% Sweep hit without charging extra special energy. Keep the second hit limited to large primary/secondary targets as appropriate.
## 66. P1/P2 - Protect from Magic does not halve Bind/Snare/Entangle durations

`SpellDefinition` gives Bind/Snare/Entangle movement locks of 8/17/25 ticks (roughly 5/10/15 seconds), and `MovementLockEffect.onApply()` always installs that full duration. It never checks whether the target is using Protect from Magic.

In the legacy ruleset, Protect from Magic halved the duration of the standard holding spells. This behaviour remained in Old School until it was explicitly removed in 2019. The server already implements the analogous target-era Tele Block rule correctly by halving its timer under Protect from Magic.

**Impact:** players using the protection prayer remain bound for roughly twice the target-era duration, materially changing Wilderness escape/chase balance.

**Fix:** for Bind/Snare/Entangle only, halve the movement-lock duration when the target is protected from Magic, while preserving the normal post-lock immunity window. Do not blindly put the prayer check inside generic `MovementLockEffect` unless Ancient-ice and NPC lock semantics are separately parameterised/tested.
## 67. P1 - Dragon axe Clobber drains ten times too much and cannot affect NPCs

`DragonAxeSpecialAttack` routes successful hits through `specialEffectId 3`. The shared effect handler immediately exits unless the target is a player, then subtracts the **full damage dealt** from both Defence and Magic.

The target-era Dragon axe/hatchet special, Clobber, used 100% special energy and lowered the target's Defence and Magic by roughly **10% of the damage dealt**. Historical descriptions also treat it as a normal combat debuff rather than a PvP-only effect.

**Impact:** against players, a 20-damage Clobber currently removes 20 Defence and 20 Magic instead of about 2 of each; against NPCs it applies no stat drain at all. The special is therefore drastically overpowered in PvP and functionally missing in PvM.

**Fix:** apply the successful-hit drain to a player/NPC stat abstraction as `floor(damage / 10)` (with the period minimum/rounding semantics verified in tests), retain the 100% energy cost, and add PvP/PvM regression cases.

## 70. Audit completion statement and boundary

The **whole-repository historical audit is complete at source/data/config/build-regression level** for the requested target of RuneScape on **18 December 2006 (revision 443)**. The audit covered the client/server build foundation, cache/maps/config definitions, player state and persistence, skills, quests, NPC/world population, drops/shops/ground items, interactions, banking/trading/economy, combat/prayers/specials/death, magic, travel, random events, Treasure Trails, minigames/activities, seasonal content, bots/custom systems and the major revision-443 interface/content migration surfaces.

The central conclusion is unchanged after the final passes: **the project has a credible revision-443 client/cache/map foundation, but the server gameplay/content layer is not yet an 18-Dec-2006 recreation.** Its largest root causes are a May-2006/revision-377 server-content horizon, mixed later/custom definition data, missing 23-skill/late-2006 schema migration, and unisolated custom/post-target systems.

This is not a claim of byte-for-byte Jagex server equivalence. Exact historical packet ordering, every animation/sound delay, every NPC dialogue line, every object option, every quest branch and every graphical interface state require targeted live-client golden playthroughs as implementation acceptance tests. The existing interaction audit itself identifies thousands of actions still needing review.

For remediation purposes, however, the audit is now sufficiently complete to start fixing in the Phase A-E order above without another broad discovery pass. New discrepancies found during implementation should be treated as local acceptance-test findings unless they reveal a new systemic root cause.
